## 회원가입과 CAPTCHA

CAPTCHA는 회원가입 폼 제출 직전에 두고, 검증을 통과해야만 가입 버튼이 활성화되도록 설계합니다. 클라이언트의 체크 상태만 믿지 말고, 가입 API에서도 CAPTCHA 토큰을 서버 측에서 재검증해야 합니다.

### 가입 단계

```text
[1. 약관 동의] ───── [2. 기본 정보 및 CAPTCHA] ───── [3. 가입 완료]
```

### 아이디·닉네임 중복 확인 규칙

아이디와 닉네임은 같은 형태로 동작해야 합니다. 한쪽에만 결과 표시가 있으면 사용자는 제출이 막힌 이유를 알 수 없습니다.

- 판정 결과는 **입력란 바로 아래에** 표시합니다. 사용 가능은 `사용할 수 있습니다.`, 중복은 `이미 사용 중입니다.`로 두 항목이 같은 문구를 씁니다.
- 값을 다시 고치면 이전 판정은 즉시 지웁니다. 확인하지 않은 값으로 가입이 진행되면 안 됩니다.
- 값이 비어 있거나 요청 중이면 `중복 확인` 버튼을 비활성화합니다.
- 닉네임은 **선택 항목**입니다. 비워 두면 중복 확인 없이 가입할 수 있고, 입력했다면 확인을 통과해야 가입 버튼이 동작합니다.
- 화면과 서버는 **같은 정규화 값**(앞뒤 공백 제거, 빈 값은 닉네임 없음)으로 확인하고 저장합니다.
  `" 단팥빵"`이 "사용 가능"으로 보인 뒤 가입 단계에서 409로 튕기는 상황을 막기 위한 규칙입니다.
- 중복 확인은 UX 편의 기능이며 최종 방어선이 아닙니다(PRD 2.4). 확인과 가입 사이의 선점은 `UNIQUE` 제약과 409 응답이 처리합니다.

## CAPTCHA 적용 원칙

- CAPTCHA 위젯은 회원가입 버튼 바로 위에 표시하고, 검증 완료 전에는 가입 버튼을 비활성화합니다.
- 이메일 인증과 CAPTCHA는 별도 검증 항목으로 유지합니다. 이메일 인증은 계정 소유 여부를, CAPTCHA는 자동화된 대량 가입 억제를 주로 담당합니다.
- 가입 API 요청 본문에는 CAPTCHA 응답 토큰을 포함합니다.
- 서버는 CAPTCHA 제공자 검증 API를 호출해 토큰의 유효성, 만료 여부, 요청 맥락을 검증한 뒤에만 회원을 생성합니다.
- CAPTCHA 검증 실패 시에도 어떤 항목이 틀렸는지 과도하게 노출하지 않고, “인증을 다시 진행해 주세요”처럼 일반화된 오류 메시지를 표시합니다.
- 반복 실패, 동일 IP의 과도한 가입 시도, 이메일 인증 발송 남용에는 별도의 rate limit을 적용합니다.
- 접근성을 위해 체크박스형 CAPTCHA 외에도 오디오 도전 과제 또는 접근성 대체 수단을 제공하는 구성이 바람직합니다.

## 개발 환경에서의 이메일 인증 확인

저장소 루트 `.env`의 `MAIL_SMTP_HOST`나 `MAIL_USERNAME`이 비어 있으면 서버는 메일을 실제로 보내지 않고, 인증 링크와 인증 코드가 포함된 본문을 애플리케이션 로그에만 남깁니다. 별도 SMTP 계정 없이도 위의 이메일 인증 화면과 가입 완료 흐름을 끝까지 확인할 수 있습니다.

따라서 개발 환경에서 「인증 코드」 입력란을 검증할 때는 받은 편지함이 아니라 백엔드 로그의 `[MAIL:DRY-RUN]` 항목에서 코드를 확인합니다. 실제 발송으로 바꾸려면 `.env`에 SMTP 값을 채우고 재기동합니다. 자세한 키 목록은 `README.md`의 「메일 발송 설정」을 참고합니다.
